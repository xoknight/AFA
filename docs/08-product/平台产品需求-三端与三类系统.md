## 一、结论先行：这不是一个货运撮合平台

国内货运平台的参与方是**客户 + 车队**两方。**跨境多了一个清关方**，所以非快达是 **三方 + 平台**：

```
        客户（货主/发货方）
              │  需求、付款、看进度
              ▼
    ┌──── 非快达平台 ────┐
    │  信息汇总 · 报价 · 分段收付 · 评价 · 风控 │
    └──┬──────────────┬──┘
       ▼              ▼
   清关公司         车队
（两头接：对客户+对车队）  （运输执行）
```

**清关公司是系统里最复杂的角色**——陈德雷原话："清关公司相当于两头接的，一方面要对接客户，一方面要对接运输公司。"

---

## 二、三类系统（下单时由客户选择组合）

| # | 系统 | 场景 | 备注 |
|---|---|---|---|
| 1 | **纯运输调度系统** | 客户自有清关能力，只要车 | 对标国内货运平台 |
| 2 | **清关 + 运输一体** | **默认形态**（"基本上清关和运输是一体的"） | Sigma 现有模式 |
| 3 | **纯清关系统** | 客户自有车队或另找运输 | 例：园区伙伴自有车 |

**产品规则**：清关公司与运输公司在平台上**永远分开注册、分开接单**，即使是同一家公司自有车队也要拆开。
> 陈德雷建议原文："平台以后来说清关公司和运输公司就分开来，就算你这个清关公司有自己的车队，也分开来，这样是最好的。" 理由：**两者要填的信息完全不同**，且客户也清楚是一家的，不影响一体化体验。

## 三、客户端：卖的是确定性

### 3.1 产品路径（六步闭环）

**清关咨询/问答 →（产生需求）→ 在线下单 → 系统报价 → 分段付费 → 全流程节点可视 → 签收 → 评价**

第一个产品是**清关咨询/问答**（即「无坑问答」）——它是流量入口，问答之后自然转化为下单需求。

### 3.2 客户到底要什么（Gavin 现场归纳，陈德雷确认）

**客户要的是确定性，具体拆成四个问题**：
1. **什么时候到**——现在到哪个节点了，预估到下一节点的时间；
2. **多了哪些费用、为什么**——每一笔费用发生在哪个节点、因何触发；
3. **为什么时间长了**——延误发生在哪一段、归因是谁；
4. **有哪些隐藏风险**——需要被提前识别出来的风险（如保额将不足）。

> 对标物：**"就跟国内的快递一样"**——打开一个订单就能看到当前进展、卡点、时间线。

### 3.3 关键功能

| 功能 | 设计要点 |
|---|---|
| 全流程节点可视 | 节点 + 时间 + 图片/视频 + 预估到下一节点时间；能打电话、有客服群 |
| **费用归因** | 每笔费用绑定触发节点与责任方。**"你延误一天，那是你的事，那跟我没有关系"——把责任边界做进产品，是责任型 3PL 最硬的护城河** |
| **官方费用直付** | 港杂、KPA、税务局费用**给客户官方账号让其自付**，平台不经手 → 可信度更高，也减少平台垫资 |
| **代付通道**（可选） | 客户无境外公司时可委托支付，平台收手续费（🟡 逐字稿提及约 5%，须核）。⚠️ 仅限可过 KYC/AML 的合规通道，见 §七 |
| 风险预警 | 保额不足、免箱期临近、承运方超载等主动弹窗 |

### 3.4 付款：分段付 + 钱包（本次达成的重要共识）

**分歧与结论**：
- 陈德雷（站用户角度）："我希望**一段一段付**。本身你也是一段一段付的，以前是你一段一段付，现在是客人一段一段付。"
- 顾虑：一个订单付多次款 → 客户公司**审批流程走不动**，反而更慢。
- **共识方案：给客户一个「钱包」**——一次性充值/审批，之后**从钱包里分段扣款**。
  - 大客户：按本批计划（如 100 条柜）预估港杂费用**整笔充入**；
  - 小客户：同样用钱包，可分批充；
  - **本质不变——仍是分段付费，只是通过钱包完成，绕开逐笔审批的摩擦。**

**纪律（Gavin 定调）**：可以分段付、可按客户分级给额度（VIP 在平台已有流水的额度高一点），**但一定要付费**——"后面已经有很多平台就是垫资垫死了"。这与在库「预充值 + 授信 + 逾期停单」的设计约束一致。

## 四、清关公司端：为什么要上平台

陈德雷的坦率回答（**这是产品要正面解决的问题**）：

> "对于我们清关公司来说，**除非你平台流量比较大、你会推客户给我，我才会积极靠拢你**。我不是需要你派单的——我不派单，我自己清、我自己干也可以。"

所以给清关公司的价值必须是三件事，缺一不可：

| # | 价值 | 说明 |
|---|---|---|
| 1 | **订单** | 平台有流量才有吸引力，这是前提 |
| 2 | **免费的清关业务系统** | 同行现用 **CargoWise**，按人头收年费——**每月 $8,000–10,000、一年好几万美金**，且**只对内、没有客户端和司机端**。平台提供免费或低价的清关系统 = 直接替其省下这笔钱 + 省人力 |
| 3 | **资金流改善** | 平台若能让客户直付港杂/KPA，清关公司就不必垫资——"你帮我们解决了一部分资金流的问题" |

> **战略判断（陈德雷原话）**："**100% 要做这个清关系统的平台。为什么？因为你想要让清关公司——不管是新的老的、大的小的——依赖于你。你的清关系统很可能是免费服务的系统，这也是你的附加值。**"
> → 这与在库「接口咽喉」战略同源：**运费可以被补贴，把同行的作业系统换成你的，补贴不出来。**

### 4.1 清关公司的能力标签与匹配

- **自填标签**：注册时自选擅长品类（设备类/大型设备/化学品/奶制品/服装/建材…）。不用 HS Code 全目录（"太大了、太细了"），**做大类即可**；
- **大数据补标签**：根据实际接单记录，为其**追加**它自己没勾选但确实做过的品类标签；
- **按货物要求推荐**：客户描述货物 → 平台匹配擅长该品类的清关公司。

### 4.2 ⭐ 承载量风控（本次最有价值的产品创意）

**问题**：有些清关公司不管自己承载量，**照单全收**，结果造成大面积延误。而"这个公司肯定不会告诉你他吃撑了"。

**解法——用历史数据推算承载量上限，双向预警**：
1. 注册时上传**资质证书 + 过往清关流量记录**（如 2025 年月均清关量、2026 年月度数据），**人工审核**后生成柱状图展示；
2. 平台据历史记录核定其**月度承载额度**（例：张三公司历史从没有一个月超过 100 条，说明能力就是 100 条）；
3. **超阈值双向提示**：
   - 对清关公司："你这个月已经接了 80%，超量了，请尽快消化，否则平台不再给你派单" → 他会紧张；
   - 对客户：选择该公司时弹窗提示"该公司本月接单已接近上限，谨慎选择"。

> 陈德雷："他就是再好的胃口，他都不敢接了。" —— **这是把「不可见的产能」变成「可定价的信用」，是平台中立性与信任度的地基。**

## 五、车队端：GPS + 还箱 + 资金

### 5.1 两个管控点

| 管控 | 现状 | 平台方案 |
|---|---|---|
| **GPS 定位** | 车队自有 GPS，**客户拿不到**；靠 WhatsApp 传图片 | **平台免费提供 GPS 给车队用**——"没多少钱，你就相当于花推广费了"。以此换取**大量车辆信息**接入 |
| **还箱管控** | 顾客最担心：车主卸完货把箱子随便一扔就没了 | **还箱凭证上传后才放尾款**；超时未还箱 → 接单受限 |

> 关于是否需要高精度定位：陈德雷认为"全方位监控是有必要的，毕竟是肯尼亚"，但目前**责任与管控都交给了供应商（车队）**。结合联畅耿卫军的建议（GPS + APP 打卡即可，不必上军用级），**MVP 阶段用平台自供 GPS + 节点打卡，不做重投入。**

### 5.2 资金：车队的真实痛点

- 车队车辆多为**银行贷款购入**，现金流紧张；
- **每次加油都是卡着路程加**——一方面防偷油，一方面确实缺钱；
- 结果：**车队要现结，客户要账期**，中间的缺口就是平台的机会。

**三级解法（由浅入深）**：
1. **平台居中协调账期**：还箱后车队即可结算，客户 7/14 天后付款，中间由平台垫付或代付；
2. **加油站授信**：平台与加油站签协议，平台车队凭额度直接加油（credit），"车队直接去加就行了"；
3. **引入银行/保险**：车队加油由银行出资，30 天后归还，银行收手续费——**风险由银行承担，平台风险降低**。

> ⚠️ 第 1 条涉及平台垫资，与「不做垫资黑洞」的红线冲突。**结论：平台只做撮合与信息，资金由持牌方（银行/保险/加油站）承担，平台不进表。** 这与在库产品边界「快付与订单融资由持牌方承担」完全一致。

### 5.3 司机端：分两类

| 类型 | 处理 |
|---|---|
| **公司端（大车队）** | 车队在后台把现有司机联系方式与车牌号填入，用司机匹配车牌号；接单时选一下即可 |
| **散户/个体户** | 直接在个人账户上自行填报 |

**信息填报的强制手段（Gavin 定调）**："你不管你是用 WhatsApp 还是什么方式，**你把信息填好给我传上来，不传上来我就不给你放款。**" —— 用结算权换数据完整性。

## 六、MVP 优先级（按「最快证明价值」排序）

| 优先级 | 功能 | 为什么排这里 |
|---|---|---|
| **P0** | 订单主数据 + 节点可视 + 一单一档（替代微信群） | 数据地基，没有它什么都免谈 |
| **P0** | **报价引擎 v1** | 税费公式已在 Excel 里跑通，直接搬；EPZ/非 EPZ 两套价目 |
| **P0** | **清关放行数 ↔ 车辆预约数对齐** | 直接消灭候车费，**当月就能算出 ROI** |
| **P1** | **保额（bond）台账 + 到期预警** | **出过三四十万美金的滞箱滞港事故**；保额生效需 7 天，纯靠人工提醒。ROI 最好讲的一个功能 |
| **P1** | 分段付费 + 钱包 + 官方费用直付 | 现金流与信任的双重支点 |
| **P1** | 车队 GPS 接入 + 还箱绑尾款 | 换数据、控风险 |
| **P2** | 清关公司标签匹配 + **承载量风控** | 平台中立性的地基，需数据积累 |
| **P2** | 评价体系（车队评价、清关公司评价） | 需交易量支撑 |
| **P2** | 供应链金融（加油授信、银行代垫） | 依赖持牌方合作 |

### 前端形态

- **清关公司 / 车队**：网页端为主 + 手机端推送；
- **客户**：微信小程序 + 网页端（B2B 付款走企业转账，不走微信支付；客户上传付款凭证）；
- 与在库《产品形态与定价体系》「系统在后台、客户在聊天里」的结论一致——**先用微信群里的数字员工跑 S1，再逐步把群里的信息流搬进系统。**

## 七、合规约束（本文所有设计的前置条件）

1. 代付通道**仅接受可过 KYC/AML 的合规资金路径**；任何形式的人民币—美元私下对敲、个人购汇拆分**一律不做**（[CLAUDE.md](../../CLAUDE.md) 红线 8）；
2. 平台费用项**不设计任何税费减免、现金小费类目**；
3. 平台**不做垫资**：快付、订单融资、保险由持牌方承担，不进平台资产负债表；
4. 承载量、评价、标签等信用类数据的展示口径需可举证，避免对第三方构成商业诋毁。
