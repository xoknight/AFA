# AFA 物流调度全流程详细字段设计 v0.3

> 日期：2026-08-08
> 输入：`物流调度需求分析-模型原文.md`、`平台产品需求-三端与三类系统.md`、`原型系统设计-v0.2.md`、Sigma 一线流程与报价材料。
> 用途：产品原型、数据库建模、接口定义和权限评审的共同底稿。本文是详细设计建议，不改写模型原文；原文待确认项继续保留。

## 1. 设计结论

系统不能把所有信息放进一张“物流订单表”。核心对象链应为：

```text
客户
  └─ 物流单 LogisticsOrder（1）
      ├─ 货柜 Container（N）
      ├─ 单据 Document（N）
      │   └─ DO ↔ 货柜（N:N）
      ├─ 清关任务 ClearanceCase（每柜 0..2+）
      ├─ 运输申请 TransportRequest（N）
      │   └─ 运输单 TransportOrder（N）
      │       └─ 车辆/司机调度 Dispatch（N）
      ├─ 还箱任务 ReturnTask（每柜 0..N）
      ├─ 费用申请 FeeApplication（N）
      │   └─ 费用明细 FeeLine / 付款 Payment / 客户应收 Receivable
      ├─ 保函占用 BondOccupation（每柜 0..N）
      ├─ 异常 Exception（N）
      └─ 状态事件 TimelineEvent（N）
```

三个闭环必须分开表达：

1. **运输闭环**：到厂、卸货、POD 完成；
2. **箱务闭环**：空箱已还、GF/还箱凭证完成；
3. **物流单闭环**：所有柜完成且保函释放、未决费用和异常清零后关闭。

## 2. 通用字段约定

除关联表外，业务表统一包含以下字段。

| 字段 | 类型 | 必填 | 规则 |
|---|---|---:|---|
| `id` | UUID | 是 | 内部主键，不向业务人员展示 |
| `tenant_id` | UUID | 是 | 租户隔离；AFA、清关公司、车队的数据边界 |
| `created_at` / `updated_at` | timestamptz | 是 | UTC 存储，界面按 Africa/Nairobi 或用户时区显示 |
| `created_by` / `updated_by` | UUID | 是 | 关联用户；机器人写入也必须落服务账号 |
| `version` | integer | 是 | 乐观锁，防止多人覆盖 |
| `is_deleted` | boolean | 是 | 业务数据软删除；默认 `false` |
| `source_channel` | enum | 是 | `WEB_ADMIN`、`CUSTOMER_H5`、`WHATSAPP`、`API`、`IMPORT`、`SYSTEM` |
| `external_ref` | varchar(100) | 否 | 外部系统幂等键 |

金额统一使用 `decimal(18,2)`，数量使用 `decimal(18,3)`；电话保存 E.164 格式；文件只保存元数据和对象存储键，不把二进制写进业务表。所有状态变化进入状态历史表，不允许只覆盖当前状态。

## 13. 状态机与转换闸门

### 13.1 物流单状态

```text
DRAFT → PENDING_ACCEPTANCE → ACTIVE → WAITING_BOND_RELEASE → COMPLETED
   └→ REJECTED             ├→ ON_HOLD
                           └→ CANCELLED
```

进入 `COMPLETED` 必须同时满足：所有必需柜已还箱并核验凭证；所有 Bond 占用已释放或标记不需要；无未关闭严重异常；必需付款/应收处理完成。任何单个布尔按钮都不能绕过闸门。

### 13.2 货柜状态

```text
WAITING_VESSEL → BERTHING → DISCHARGING → WAITING_YARD_TRANSFER
→ AT_YARD → CLEARANCE_IN_PROGRESS → RELEASED
→ TRANSPORT_BOOKED → IN_TRANSIT → AT_FACTORY
→ UNLOADING → WAITING_EMPTY_RETURN → RETURNING_EMPTY
→ EMPTY_RETURNED → BOND_RELEASING → CLOSED
```

原七状态作为大屏聚合标签保留：等待船舶靠港、卸柜中、等待运送至堆场、清关中、运输中、已到场、还箱中；底层使用更细状态，避免无法判断责任和超时起点。

### 13.3 运输单状态

```text
PENDING_ACCEPTANCE → ACCEPTED → VEHICLE_CONTACTED → DRIVER_ASSIGNED
→ READY_TO_DEPART → IN_TRANSIT → ARRIVED → POD_PENDING → COMPLETED
```

可从未出发状态进入 `POSTPONED` 或 `CANCELLED`。写入 `actual_departure_at` 后开始 36 小时计时；达到 `COMPLETED` 仅表示本次运输完成，不代表物流单或保函完成。

| `TRANSPORT_DEPARTED` | 启动 GPS 与 36 小时监控 |
| `CONTAINER_UNLOADED` | 创建还箱任务，状态进入等待还箱 |
| `FEE_PAYMENT_CONFIRMED` | 更新费用申请；滞箱费场景通知业务员补 GF |
| `EMPTY_RETURN_VERIFIED` | 允许车队尾款；触发保函释放资格检查 |
| `BOND_RELEASED` | 释放额度；检查物流单关闭条件 |
| `CUSTOMER_RECEIVABLE_SETTLED` | 由财务确认释放账期额度 |
| `HELP_REQUEST_CREATED` | 发给上级并进入待办 |

事件处理必须幂等，并记录业务对象版本；通知失败不回滚业务事实，但进入重试队列。

## 18. MVP 建议落地顺序

### P0：先让流程和数据跑通

`organization`、`user`、`customer_profile`、`logistics_order`、`container`、`document`、`document_check_item`、`clearance_case`、`transport_request`、`transport_order`、`dispatch_assignment`、`timeline_event`、`exception_case`。

### P1：完成履约闭环

场地作业、还箱任务、POD/还箱凭证闸门、费用申请/审批/付款、客户应收、额度台账、Bond 占用释放、预警规则。

### P2：经营与智能化

钱包、差价规则、GPS 接口、合作方承载量、客户评价、预测快照、AI 字段抽取与异常摘要。

## 19. 仍需业务确认的问题

1. 原模型中的“柜子在堆场清关一次、到厂区后第二次清关”在肯尼亚业务中的正式业务/海关术语、适用订单类型与凭证；
2. IDF、GF、Entry Paper 在不同服务类型、客户和货类下的必填时点；
3. 费用差价规则：固定加价、比例、阶梯、客户协议或逐单报价，以及税务口径；
4. 账期与 Bond 是客户独立额度还是部分共享额度；额度冻结、占用、释放的审批人；
5. “已还柜作为运输单完成”与“POD 后运输完成”的管理口径，应保留两个里程碑还是按业务类型切换；
6. 滞箱费、滞港费的区分、责任归因和客户转收费审批；
7. 原“小费”类费用的合规处理：建议禁止普通申请，改为异常现金支出并走双人审批；
8. 场地部门是否是 AFA 内部部门、客户工厂人员，或外部堆场伙伴，以决定租户与数据权限；
9. 港口数据、船司船期、GPS、WhatsApp 和支付渠道的实际接口能力。

以上问题不阻断 P0 原型，但在数据库迁移冻结和财务上线前必须确认。
